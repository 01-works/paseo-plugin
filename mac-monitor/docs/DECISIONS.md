# 구현 결정 및 계획 보완

현재 자동 관리 범위는 마지막 0.4.0 결정과 [PLAN 15절](PLAN.md)을 따른다. 아래 이전 결정은 변경 이력이다.

## 2026-10-06 · 지속 압력 리뷰·개별 worker 자동 관리 (PLAN 13절)

사용자가 지속 압력의 Luna 리뷰 및 검증된 대상 자동 종료를 요청했고, 허용 대상은 제안해 달라고 했다.
첫 범위는 **직접 지정한 독립 개발 worker의 실행 인스턴스**다. 허용 목록은 비어 있으며
`PID + 시작 시각 + 실행 경로 + 그룹 + 이름`으로 묶어 다른 작업과 재실행된 프로세스에 권한이 이어지지 않는다.
Node/Python 런타임 전체나 앱 그룹을 전역 허용하지 않는다. 허용 시 네이티브의 소유자·상위 프로세스 검증이 필요하며
Codex/Claude 작업의 자식과 Paseo의 보호된 트리를 공유하는 다른 플러그인도 차단한다. 기존 수동 종료 절차는 유지한다.

압력 `critical` 120초 + 약 60초 footprint 증가가 기본이다. 정상 압력에서는 기존 시스템 샘플 콜백만 관찰한다.
PLAN 4.5의 UI 관심 외 스캔 금지에는 이번 요청으로 최대 150초 자동 조사 예외를 추가했다.
UI와 조사는 헬퍼 한 개의 2초 타이머를 공유하고 각자의 관심을 해제한다.
AI는 후보 4개·동시 1개·45초·15분 대기·24시간 6회로 제한한다. 가용 수준 3% 미만/미확인,
CPU 85% 이상, 디스크 여유 1 GiB 미만/미확인은 조사·리뷰도 보류하며 진행 중 리뷰를 취소한다.
작업 목적을 모르면 observe로 판단하도록 지시하고 낮은 CPU나 물리 RAM보다 큰 footprint만으로 이상이라 판단하지 않는다.

Paseo 0.10.2의 공개 API 대신 기존 로그인 **Codex CLI 0.160.0**의 읽기 전용 일회성 실행을 사용한다.
모델은 요청한 `gpt-6-luna`를 유지하며 다른 모델로 자동 대체하지 않는다.
셸·MCP·웹·앱·훅·프로젝트 규칙·외부 스킬·서브에이전트·이미지/컴퓨터 제어를 제외하고 구조화 JSON만 받는다.
모델에는 이름·PID 식별 키·수치/추세·허용 여부만 보내고 전체 경로·명령행·파일/작업 내용은 보내지 않는다.
전역 Codex 설정·인증 파일은 수정하지 않고 플러그인이 API 키를 수집하지 않는다.
[Codex 비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode),
[CLI 설정](https://learn.chatgpt.com/docs/config-file/config-reference),
[GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).

`skip_host_skill_discovery`는 CLI 0.160.0의 개발 중 기능으로 시작 컨텍스트 비용을 줄이기 위해 해당 실행에만 켠다.
같은 명령의 `suppress_unstable_features_warning=true`로 시작 경고를 끈다.
이 CLI는 꺼 둔 Code Mode 호스트의 비활성 안내도 error item으로 내보내므로 **해당 시작 안내의 알려진 접두사만** 허용한다.
다른 오류·turn.failed·도구 이벤트는 중단한다. 실제 Luna 호출에서 도구 없이 observe JSON을 받아 검증했다.
옵션 또는 모델을 지원하지 않는 CLI/계정은 오류를 기록하고 이번 조치를 중단한다.

모델은 종료 실행 권한을 갖지 않는다. 코드는 최신 압력·추세·CPU·PID/시작/경로·허용을 다시 확인하고,
허용을 소비·저장한 다음 네이티브 재검사를 거쳐 SIGTERM 하나만 보낸다. 10초 후 해당 PID만 조회해 결과를 기록한다.
상위 목록 이탈·조회 권한 실패를 성공으로 쓰지 않고 한 리뷰에서 연쇄 종료하거나 SIGKILL을 추가하지 않는다.
공개 신규 설치는 꺼짐, 이 Mac은 사용자 요청에 따라 리뷰 켜짐으로 설정한다. 허용 목록이 비어 있으면 리뷰만 한다.
설정·예산·기록은 `~/.paseo/mac-monitor/automation.json`에 보존하며 글로벌 Paseo 설정은 수정하지 않는다.

사용자의 자동 종료 로그 요청은 반영한다. 최근 20개 화면 기록과 별도로
`automatic-actions.jsonl`에 PID·시작 시각·실행 경로·Luna 결정/근거·전후 압력/메모리·종료 결과를 남긴다.
이는 로컬 기록이며 전체 경로는 모델로 보내지 않는다. 0600 권한, 256 KiB 단위 교체와 이전 파일 하나로 약 512 KiB를 제한한다.
리뷰·종료 사건만 기록하므로 정상 상태에 파일 쓰기를 추가하지 않는다. 종료 예정 기록을 fsync한 뒤 SIGTERM을 보내며
기록 저장 실패는 자동 조치를 중단한다. 신호 전송과 실제 종료를 구별하고 조회 실패/알 수 없는 값은 성공/0으로 바꾸지 않는다.
이유는 모델 판단·대상 검증·신호 전송 중 어디서 멈췄는지 사후 확인할 수 있어야 하기 때문이다.

디스크 부족의 작업 자동 중단은 제외했다. 용량만으로 소비 주체·작업 저장 상태를 알 수 없고 별도 추적은 저부하 목표에 맞지 않는다.
기존 statfs 30초 값으로 여유 2 GiB 미만만 표시하고 리뷰도 1 GiB 미만이면 보류한다.
디스크 부족만으로 에이전트·다른 작업 공간을 멈추거나 파일을 삭제하지 않는다.

## 2026-10-06 · 서버의 설치 경로 탐색 (PLAN 5.2, 12절)

Paseo v0.10.2 `packages/server/src/server/plugins/compiler.ts`는 CommonJS 번들을 만들고,
`plugin-process.ts: evaluateBundle`은 `globalThis.eval`로 실행한다. 서버 컨텍스트에는
소스 경로나 데이터 디렉터리가 없으며 `import.meta.url`을 사용할 수 없다.

따라서 `PASEO_HOME`(없으면 `~/.paseo`)의 `config.json`에서 **mac-monitor 항목의 path만 읽어**
설치 디렉터리를 찾는다. 설정 파일을 직접 수정하지 않는다. `server-id`도 동일한 홈에서 읽는다.
설정 경로를 찾을 수 없으면 Node 모드로 폴백한다. `--id`로 다른 ID 설치는 지원하지 않는다.
테스트와 수동 대조 CLI는 root를 주입한다.

## 2026-10-06 · 오류 및 시계 처리 보완 (PLAN 5.2, 6절)

신선도는 서버 단조 시계 기준으로 판정하며 화면의 갱신 시각은 헬퍼의 절대 시각을 사용한다.
시계 조정으로 오래된 값이 정상 상태가 되는 것을 막는다. 메모리/CPU API 실패는 해당 값을
null로 표시하고 오류 상태를 반환한다. 압력만 실패하면 압력은 확인 불가이며 다른 수치는 유지한다.
프로세스 CPU는 PID/시작 시각이 같은 항목의 차이를 합산한다. 새 프로세스의 누적 CPU나 종료된
프로세스 때문에 그룹 CPU가 역행하는 것을 막기 위한 것으로 승인된 그룹별 Δ 공식의 구현 방식이다.

## 2026-10-06 · 부하 검증 방식 (PLAN 9.3절)

9.3절의 `ps` 관찰 예시 대신 사용자 제약(주기적 ps/top 금지)을 우선하여,
`test/manual/measure-load.c`로 libproc CPU 누적값을 관찰 시작·종료 두 번만 읽는다.
시간 변환에는 `mach_timebase_info`를 적용하며 RSS는 종료 시 `PROC_PIDTASKINFO`로 읽는다.
시스템 전용 / 앱 스캔 활성 모드를 각각 120초 관찰한다.

## 2026-10-06 · Node 폴백 실행 비용 (PLAN 5.2절)

2초마다 `vm_stat` 한 번과 여러 키를 함께 읽는 `sysctl` 한 번만 실행한다.
일부 sysctl 키 실패 시 성공한 stdout 키는 보존하며 누락된 필드만 null과 오류로 처리한다.
프로세스 상위 목록은 미지원이다. 리서치의 0.11%는 프로토타입 비용이며 이 구현의 보장 수치가 아니다.

## 2026-10-06 · pill 잘림 및 좁은 상세 창 수정 (PLAN 5.3절 변경)

사용자가 상세 창의 펼침 방향과 좁은 폭, RAM 잘림을 보고해 UI 개선을 요청했다.
v0.10.2 `packages/app/src/plugins/buttons/view.tsx`에서 pill은 `maxWidth: 160`,
라벨은 한 줄로 제한된다. 팝오버는 별도로 `minWidth=280`, `maxWidth=420`이며
composer 위쪽을 선호하지만 공간에 따라 위치가 달라질 수 있다. SDK에는 폭·방향 지정 옵션이 없다.

일반 화면에도 계획의 축약 라벨 `23% · 14.1G`를 적용하고 전체 용량은 상세에 유지한다.
`G`는 GiB이며 버튼 설명에도 단위를 명시한다. 요청에 따라 popover 대신 공식 0.10.2
`Modal`과 action 버튼을 사용한다. 데스크톱 기본 중앙 모달 폭은 최대 520px이고 compact는
호스트의 시트를 따른다. 고정 최소 폭을 제거하고 긴 CPU 설명을 두 행으로 나눠 좁은 화면의
넘침을 줄인다. 모달은 열린 동안만 내용을 mount하여 상세 폴링·앱 스캔 관심 규칙을 유지한다.
수집기·샘플 간격은 변경하지 않는다. 실제 테마·compact 화면 확인은 여전히 사용자 확인이 필요하다.

## 2026-10-06 · 시각적 정보 구성 (PLAN 5.3절 보완)

사용자가 텍스트 위주 화면의 가독성 개선을 요청했다. `paseo-top` 0.4.3의
`client/pill.tsx` System 탭 및 helper의 Card/ProgressBar/MetricGauge 구성을 참고하여
큰 숫자·카드·사용량 막대·메모리 범례·상위 앱 탭을 직접 구현했다. 레퍼런스 코드는 복사하지 않았다.

React Native 기본 요소로 같은 레이아웃을 구현할 수 있어 추가 UI/차트 라이브러리는 넣지 않는다.
레퍼런스의 웹 conic-gradient 및 사용률 임계값에 따른 상태 색은 승인 계획의 DOM/색 규칙과
맞지 않아 도입하지 않는다. 새 타이머·수집·RPC는 없고 탭 전환은 화면에 받은 목록만 바꾼다.

CPU·물리 메모리·스왑 막대는 전체 값 대비 크기다. 구성 막대는 앱/와이어드/압축이며 캐시는 제외한다.
드물게 구성 합계가 물리 용량을 넘으면 사용량에 맞춰 구성 막대만 정규화하고 화면에 알린다.
앱 메모리 막대는 목록 내 최대 footprint 기준으로 비교하며 물리 RAM 비율로 표현하지 않는다.
누락값은 —와 빈 점선 막대, 이전 값은 지연/오류 표시와 흐린 막대로 구별한다.
상태 색은 OS 압력 배지/점에만 쓴다. compact에서는 주요 카드와 호스트 정보를 세로로 쌓는다.

`test/manual/ui-preview.mjs`는 실제 React 컴포넌트 트리를 HTML로 옮기는 레이아웃 검토 도구다.
출력은 `/tmp/mac-monitor-ui/`에 생성하며 HTML은 클라이언트 번들에 포함하지 않는다.
예시 데이터/예시 테마의 정적 검토이며 실제 Paseo·모바일 화면 검증을 대체하지 않는다.

## 2026-10-06 · 기본 폰트와 스크롤 가능한 상위 10개 (PLAN 1, 2, 5.3절 변경)

사용자 요청으로 모든 client의 `fontSize` 지정을 제거하여 React Native 기본 크기를 사용한다.
큰 수치·장식용 MAC 타일을 제거하고 카드 여백과 모서리도 줄였다. 기본 크기로 제목·수치·각주를
표시하며 범례·막대와 압력 색 규칙은 유지한다.

앱 목록은 CPU·메모리 각각 최대 10개로 늘린다. C 헬퍼 출력 한도, RPC 스키마 한도,
화면 표시를 함께 변경하고 universal prebuilt 바이너리를 다시 빌드·서명한다.
프로세스 스캔·정렬 방식, 2초 주기, 30초 관심 유지 규칙은 변경하지 않는다.
목록 내부는 최대 높이 320의 스크롤 영역으로 제한하고 0.10.2 공식 ScrollView를 사용해
모바일 시트의 스크롤 제스처를 호스트에 연결한다. 부하 수치는 이전 상위 5개 버전의 실측이며
이번 출력 확장 후 다시 측정한 값으로 표현하지 않는다.

## 2026-10-06 · 안내 문구 축소와 앱 목록 높이 고정 (PLAN 5.3절 변경)

사용자가 용량 단위/Activity Monitor/footprint 안내 문구 제거와 로딩 중 높이 변화를 해결하도록 요청했다.
해당 화면 각주를 제거하고 설명은 README에 유지한다. CPU 범위·메모리 합 공식·캐시 제외·압력 색 규칙의
반복 설명도 화면에서 제거했다. 갱신 시각은 헤더에 상대 시각과 시각을 모으고 전체 날짜는 접근성 설명으로 제공한다.
가용 비율·root/권한 제외 수·오류·지연 표시는 유지한다. 앱 메모리 막대의 상대 비교는 짧은 라벨로 구분한다.

앱 ScrollView는 최대 높이 대신 `height: 320`, `flexGrow: 0`, `flexShrink: 0`으로 고정한다.
로딩/빈 목록/미지원 메시지와 실제 목록 모두 같은 영역 안에 렌더한다. 제외 수 역시 목록 내부에 두어
데이터 도착으로 카드 높이가 늘어나지 않는다. 최초 RPC 결과가 없는 때에도 —를 사용하는 같은 카드 구조를
표시하여 첫 로딩에서도 목록 공간을 확보한다. 추가 측정·타이머는 없다.

## 2026-10-06 · pill 툴팁 축소와 수동 갱신·복사 (PLAN 5.3, 5.4절 변경)

사용자가 반복되는 “Mac 시스템 모니터…” 문구와 자동 갱신 중 텍스트 복사 불편을 보고했다.
v0.10.2 호스트의 `plugins/buttons/view.tsx`는 pill의 `button.title`을 툴팁으로 자동 표시한다.
SDK에 툴팁 비활성화 옵션이 없고 `buttons/validation.ts`는 빈 제목도 거절한다.
따라서 긴 안내 제목을 “모니터”로 축소하고 상세 모달 제목도 맞춘다. 툴팁 자체를 제거했다고 표현하지 않는다.

사용자가 자동 갱신 자체가 불편하다고 명확히 요청했다. 상세 모달과 대시보드의 2초 폴링을 제거하고,

## 2026-10-06 · CPU·메모리 통합 배치와 pill 값 즉시 표시 (PLAN 5.3절 변경)

기다리는 RPC가 끝나기 전까지 시스템 값도 비워 뒀다. pill은 이미 가진 Snapshot을 Modal에 전달하며,
상세의 로컬 상태를 이 값으로 한 번만 초기화한다. 사이드바도 동일 호스트의 공유 요청 캐시로 초기화한다.

오른쪽 여백 8을 확보하고 순위 열 제목도 같은 여백으로 정렬한다.
실제 작은 footprint가 `0.0 GiB`로 표시돼 0처럼 읽히는 점도 확인했다. PLAN의 GiB·소수 1자리 규칙을 보완하여
0보다 크고 0.1 GiB 미만인 값만 `<0.1 GiB`로 표시한다. 실제 0은 `0.0 GiB`, 누락은 `—`를 유지한다.
단위·정확한 원시 값·측정 공식·측정 비용 구조는 바꾸지 않는다. 별도 UI 기능이나 라이브러리는 추가하지 않는다.

## 2026-10-06 · Activity Monitor 직접 대조 뒤 메모리 공식 유지 (PLAN 4.1, 9절)

사용자의 직접 확인 요청으로 Activity Monitor와 비교 CLI를 같은 시각 근처에서 대조했다.
두 관찰 쌍에서 앱·와이어드·압축·캐시·스왑 차이는 항목별 0.02 GiB 미만이었지만,
Activity Monitor의 총 사용량은 약 0.56 GiB 높았다. Activity Monitor 화면 자체에서도
총 사용량이 세 구성 항목 합보다 0.56~0.57 GiB 높아 단순 반올림·시각 차이로만 설명할 수 없다.

현재 구현은 승인된 `앱 + 와이어드 + 압축` 식을 정확히 사용한다. Activity Monitor 내부 합계와
해당 차이의 카운터 대응은 확정하지 못했으므로 예약 영역 등으로 원인을 단정하지 않는다.
추측으로 보정하거나 기존 금지 방식인 `total − free`로 바꾸지 않는다. 계산식 변경 결정은 하지 않았으며
관측 사실·시각·남은 한계를 VALIDATION.md와 README에 공개한다.
따라서 PLAN의 “Activity Monitor 사용된 메모리에 대응”은 의미상의 목표이며 총 수치의 동일성을 보장하지 않는다.

## 2026-10-06 · 메모리 합계 차이 원인 확인 (PLAN 4.1, 9절 보완)

사용자가 원인 조사를 요청했다. 설치된 Activity Monitor와 sysmond의 arm64e·x86_64 실행 파일을
읽기 전용으로 추적해 이 빌드의 Activity Monitor 합계가
`hw.memsize − (free_count − speculative_count + external_page_count) × page`임을 확인했다.
이는 제품의 `앱 + 와이어드 + 압축` 식과 다르다. 같은 원시 카운터 100회에서 차이는 0.538~0.587 GiB였다.

이 Mac의 `hw.memsize − hw.memsize_usable`은 0.510208 GiB이며 해당 XNU 버전의 공식 소스는 이를
carveout을 제외하기 전후의 차이로 설명한다. Activity Monitor 합계는 이 영역을 포함하며 purgeable을
추가로 빼지 않는다. usable RAM과 VM 카운터 합의 작은 잔여 차이도 관찰했지만 그 영역까지 특정하지 않았다.
근거와 재현 방법은 [합계 차이 조사](research/report-memory-accounting.md)에 기록했다.

이번 요청은 원인 조사이며 제품의 계산식 변경 결정은 하지 않았다. PLAN 4.1절의 식을 유지한다.
이전 절의 “원인 미확정”은 직접 화면 대조 당시의 상태로 남기고 README·VALIDATION의 현재 설명을 갱신했다.
Activity Monitor 기준으로 전환한다면 구성 바와 합계의 관계, 오류 처리, Node 폴백도 함께 변경해야 한다.
추가로 필요한 speculative 값은 기존 VM 조회 응답에 있으므로 새 프로세스 스캔이나 비공개 API는 필요 없다.

## 2026-10-06 · Activity Monitor 기준 메모리 합계 개선 (PLAN 4.1, 5.1, 5.3, 8절 변경)

원인 조사 뒤 사용자가 "개선 되나?"라고 요청했다. 후속 개선 지시에 따라 총 사용량을
`hw.memsize − (free_count − speculative_count + external_page_count) × page`로 변경한다.
이 Mac의 Activity Monitor 실행 파일에서 확인한 식이며 이전 합계의 약 0.56 GiB 차이를 상수 보정 없이 해결한다.
최초 승인 식과 다른 이유·원시 값·출처는 [합계 차이 조사](research/report-memory-accounting.md)에 있다.

헬퍼는 이미 읽은 HOST_VM_INFO64의 speculative_count만 JSON에 추가한다. VM 조회 횟수와 2초 고정 타이머,
앱 관심 30초·디스크 조회 30초는 그대로다. 비공개 API와 새 프로세스 스캔은 도입하지 않는다.
Node 폴백의 vm_stat "Pages free"는 이미 speculative을 제외한다는 Apple 공식 소스를 확인했다.
같은 출력의 "Pages speculative"을 더해 Mach free_count를 복원하므로 이중 차감하지 않는다.
[Apple vm_stat 소스](https://github.com/apple-oss-distributions/system_cmds/blob/main/vm_stat/vm_stat.c#L126).

앱·와이어드·압축·캐시 수치는 유지한다. 사용량과 캐시는 일부 중첩하고 세부 항목 합은 총 사용량과 다르므로
메모리 막대를 총 사용량/물리 메모리의 단일 막대로 간소화한다. 색은 OS 압력 기준이며 아래에 세부 수치를 유지한다.
분류를 확정하지 않은 "기타" 수치·설명 각주·새 버튼은 화면에 추가하지 않는다. 기본 폰트·고정 앱 목록 높이도 유지한다.

speculative 누락이나 카운터 역행·음수 합계·안전한 정수 범위 초과는 메모리 null과 오류로 처리한다.
이전 v1 헬퍼의 누락 필드는 CPU 등 다른 값을 읽을 수 있도록 null로 해석하며 헬퍼 업데이트 사유를 표시한다.
Node에서 항목을 읽지 못해도 0으로 대체하지 않는다. 제품 버전은 0.1.1이며 Paseo SDK/manifest 최소 버전은 0.10.2를 유지한다.

## 2026-10-06 · 스왑 표시 검토 (PLAN 2, 4.3, 6절 보완)

사용자가 스왑의 필요성과 현재 구성의 적절성을 물었다. 기존 미니멀 화면 요구에 맞춰 상세와
데스크톱 호스트 표의 스왑을 `사용량 / 전체`에서 사용량만 표시하도록 간소화한다. compact 호스트 카드는
이미 사용량만 표시하므로 두 화면의 기준도 통일된다. pill에는 CPU·사용 메모리를 유지한다.

스왑은 RAM과 디스크 사이의 메모리 관리 상태를 이해하는 보조 정보다.
[Apple 설명](https://support.apple.com/ko-kr/guide/activity-monitor/actmntr1004/mac)은 스왑 사용 공간을 별도로 제공하며,
메모리 압력을 여유 메모리·스왑률·와이어드·캐시를 함께 반영하는 값으로 설명한다.
스왑 총량은 현재 할당된 세그먼트로 계산되고 고정 최대 용량과 별도다.
[XNU 구현](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/osfmk/vm/vm_compressor_backing_store.c#L2263).
전체 수치나 비율을 강조하면 고정 용량 대비 포화율로 오해할 수 있으므로 화면에서 생략한다.

스왑 값만으로 위험 색을 부여하지 않는다. RPC·대조 CLI의 used/total, 기존 수집기와 측정 주기는 유지하며
새 조회·라이브러리·상태 문구는 추가하지 않는다. 누락값은 기존처럼 `—`로 표시한다.

## 2026-10-07 · 자동 리뷰·확인 종료로 단순화하고 실험 집계 제거 (0.3.0, PLAN 14절)

측정 실패·지연은 거절한다. 압력이 회복되거나 자동 리뷰를 꺼도 최신 대상의 명시 확인은 가능하다.

확인 종료도 시도 상태와 예정 로그를 먼저 저장하고 SIGTERM을 한 번만 요청한다.
기존 상세 로그에 `mode: confirmed`와 리뷰 시각을 추가해 자동 조치와 구분하며 10초 후 PID를 직접 조회한다.
재시작·통신 실패·플러그인 종료로 확인하지 못한 결과는 unknown으로 남기고 신호를 재전송하지 않는다.
기존 독립 worker의 일회 자동 종료 허용은 선택 사항으로 유지하며 화면에서 **자동 종료 허용**으로 구분한다.
상태 파일 v1은 새 리뷰 목록 누락을 빈 목록으로 읽어 기존 설정·허용·호출 예산을 보존한다.

`client/fleet/`의 globalThis 레지스트리·집계 표·설정과 서버의 serverId 파일 읽기를 제거했다.
조회·종료는 공식 호스트 선택기의 선택한 Mac에 적용한다. 공식 SDK의 연결 상태·에이전트 수만 남긴다.
호스트 전환 테스트에서 이전 hostname이 남는 현상을 재현해 화면을 호스트별로 새로 구성하고
host-info query key도 호스트별로 나눴다. 오프라인 호스트에는 다른 Mac의 값을 대신 표시하지 않는다.
기존 데몬의 `experimentalFleet` 설정은 읽지 않으며 전역 설정 파일을 직접 수정하지 않는다.

네이티브 측정 코드·바이너리, 2초 간격·30초 관심·디스크 조회, 모델·자원 보류·호출 예산은 그대로다.
새 라이브러리·감시 타이머·정상 상태의 추가 수집은 도입하지 않는다.
확인 종료는 직접 만든 검증용 자식으로만 시험했으며 실제 임계 압력의 전체 흐름은 유발하지 않았다.
검증 결과와 남은 실제 화면 확인은 [VALIDATION.md](VALIDATION.md)에 기록한다.

## 2026-10-07 · 자동 감시·리뷰·종료 제거 (0.4.0, PLAN 15절)

사용자가 자동 관리와 별도 확인 절차의 필요성을 재검토했다. 시스템 수치·상위 앱·수동 종료만 남기자는
제안에 "진행"으로 승인했으므로 13·14절의 자동 관리 부분을 제거한다. 압력 추세·후보·허용·예산·로그를
유지하는 복잡도와 AI 호출 비용에 비해 이 플러그인의 미니멀한 저부하 모니터 목적에 맞지 않는다는 판단이다.

자동 리뷰 화면·Luna CLI 실행·일회 허용·후보 확인 RPC·전용 상태 저장·종료 후 조회와 관련 검증 도구를 제거한다.
자동 조사용 앱 스캔 관심과 수집기 구독도 제거하여 UI의 마지막 목록 요청 30초 뒤 스캔이 꺼지게 한다.
C 헬퍼는 자동 종료·검증·조회 명령을 받지 않으며 그룹 이름만 캐시한다. 전체 실행 경로를 보관·전송하지 않는다.
제거된 RPC/필드가 있으므로 기능 버전은 0.4.0으로 올리며 SDK와 manifest 최소 버전은 0.10.2를 유지한다.

시스템·디스크 측정 공식과 2초/30초 주기, 상위 10개·기본 폰트·고정 목록 높이·화면 자동 갱신을 유지한다.
개별·앱 그룹 수동 종료는 기존 확인창 한 번과 그룹/PID/시작 시각·현재 UID·자신/Paseo/상위 프로세스 검증을 유지한다.
신호 전송 성공을 실제 종료 완료라고 표시하지 않으며 강제 종료는 추가하지 않는다.
공식 호스트 선택기와 에이전트 수는 유지하고 0.3.0에서 제거한 실험적 집계는 복원하지 않는다.

기존 전용 설정·자동 조치 로그는 기록 보존을 위해 삭제하지 않는다. 0.4.0은 이를 읽거나 쓰지 않으며
전역 설정과 다른 플러그인도 수정하지 않는다. 최신 검증과 직접 확인이 남은 항목은 [VALIDATION.md](VALIDATION.md)에 기록한다.

## 2026-10-07 · 요청할 때만 Luna 정리 검사와 공식 기기 전환 (0.5.0)

사용자가 상시 관리의 복잡도 없이 오래 남은 작업을 정리하고 싶다고 했다. 요청할 때 잠깐 관찰하고
Luna가 후보를 설명한 뒤 사용자가 선택해 종료하는 제안과 기기 전환을 "둘 다 진행해줘"로 승인했다.
새 범위는 [PLAN 16절](PLAN.md)에 기록했다. 장기 비활동을 확인하려면 상시 관찰이 필요하지만 이번 기능은
실행 시간과 약 12초의 현재 활동만 판단 근거로 사용한다. Luna의 의견은 작업이 끝났다는 보장이 아니다.

Paseo 0.10.2 SDK에는 본문에서 선택 호스트를 바꾸거나 다른 호스트의 플러그인 RPC를 부르는 공개 API가 없다.
v0.10.2 `surface-screen.tsx`의 기본 선택기는 해당 플러그인의 화면이 두 호스트 이상에 등록되어야 표시된다.
공식 상단 선택기를 유지하고 현재 기기와 호스트별 요청/검사 수명주기를 보강한다. 다른 Mac의 설치·조작,
전역 설정 변경, 실험적 레지스트리 복원은 수행하지 않는다.

관찰은 실행 30분 이상·footprint 8 MiB 이상·현재 CPU 0.1% 이하의 현재 사용자 프로세스를 우선하며
최대 128개·그룹당 4개를 전송한다. 이후 연속 6개 이상의 샘플·10초 이상 관찰한 대상 중
최대 16개·그룹당 2개만 실행 정보를 읽고 검토한다. 숫자는 검사 부하와 모델 입력을 제한하기 위한
초기 범위이며 장기 유휴의 정의가 아니다. 디스크 I/O는 기존 `RUSAGE_INFO_V4`의 관찰 구간 차이만
참고하고, 평소 표시·디스크 작업 추적·장기 저장은 추가하지 않는다.

`KERN_PROCARGS2`에서 실행 인자만 읽는다. Apple XNU의
[sysctl](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sysctl.c)과
[exec_extract_strings](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_exec.c)를 확인해
실행 경로 뒤의 포인터 폭 정렬과 정확한 argc를 따른다. 단순히 NUL을 전부 건너뛰면 빈 argv[0] 뒤의
환경 영역을 인자로 오인할 수 있어 32/64비트·빈 인자·빈 argv[0]·잘린 데이터의 C 회귀를 추가했다.
32개/각 512 bytes를 넘는 인자는 일부만 읽지 않고 확인 불가로 제외한다.

모델은 기존 Codex 인증을 사용하는 `gpt-6-luna` 한 번이며 45초 제한, 도구 비활성,
읽기 전용 임시 폴더, 구조/입력 대상 일치 검증을 적용한다. 결과 만료는 단조 시계 기준 10분이다.
실행 정보를 읽는 동안 관찰 캐시를 유지하고 모델 대기 전에 해제한다. 정보 읽기 실패와 취소는
빈 정상 결과로 바꾸지 않으며, 신호 전송 전에 전체 선택의 실행 정보와 현재 CPU를 재확인한다.
후속 사용자 판단이 필요한 범위 확장은 없으며 자동 관리 제거 원칙을 유지한다.

## 2026-10-07 · 요청형 정리 검사를 돕는 1시간 숫자 이력 (0.6.0)

사용자의 짧은 평소 이력 제안과 방향 리뷰 요청을 검토했다. 요청할 때의 12초만으로는 직전 활동을
놓치지만, 전체 실행 정보나 영구 로그를 남기는 것은 저부하·미니멀 목적에 비해 과하다.
따라서 [PLAN 17절](PLAN.md)의 1분 간격·최근 1시간 숫자만 보관하는 범위로 16절을 변경한다.
이력만으로 실제 이용 여부를 판정하지 않으며 AI 호출·종료는 계속 요청/확인 때만 수행한다.

상위 앱만 기록하면 footprint가 작은 Node 서버를 놓친다. 현재 사용자의 8 MiB 이상 프로세스를
최대 512개 수집하고, 상한 때문에 빠진 대상은 비활동으로 취급하지 않는다. 앱 화면의 스캔을
재사용하며 화면이 닫히면 같은 헬퍼에서 분당 한 번 숫자만 읽는다. 주기적 실행 경로·이름·
명령행·작업 폴더·환경 변수 조회와 별도 헬퍼는 추가하지 않는다.

최대 61회 값을 typed array로 저장해 숫자 버퍼를 1,374,208 bytes로 제한한다.
프로세스별 JS 객체를 한 시간 누적하는 대신 고정 폭 숫자 배열을 사용해 메모리 상한을 분명히 한다.
수집 누락·재사용·역행·수면/시계 불연속은 연속 관측을 끊고, CPU 구간 최대도 1분 평균의 최대라고
명시한다. 정상 대기 서버의 사용 여부·순간 활동·네트워크/GPU는 이 값만으로 확정할 수 없다.
배경 부하는 새 버전으로 실측한 뒤 README/VALIDATION에 기록하며 기존 앱 스캔 수치로 대체하지 않는다.

실제 화면 검토에서 Claude의 네이티브 버전 실행 파일이 basename 보호를 우회하는 기존 경계를 발견했다.
기존에 승인한 Claude 보호를 적용하도록 `/claude/versions/`·`/.claude/versions/` 경로와
Paseo/Codex/Claude 그룹을 검사 및 확인 종료에서 제외한다. 보호 범위를 완화하거나 자동 종료를 추가하는 변경은 아니다.
